Pull Request Anatomy & Review Hygiene

An executive reference for code review mechanics, reviewer etiquette, and review velocity.

The 5 Components of a Pull Request (PR)

Component What It Contains & Why It Matters
1. Context & Description The "Why" behind the change: user story link, architectural rationale, screenshots for UI changes, and testing instructions.
2. Code Diff The side-by-side comparison of modified files showing green additions (+) and red deletions (-).
3. CI Status Checks Automated bots reporting whether tests passed, linters succeeded, and security vulnerability scans are clean.
4. Inline Comments Specific conversations pinned to exact code lines for clarifying edge cases, security risks, or naming improvements.
5. Approval & Merge Gate The final sign-off (e.g. "LGTM" / Approved) required by repository protection rules before code is merged into main.

The Law of PR Sizing

The Mammoth PR (500+ Lines)

The Phenomenon: Cognitive overload sets in. Reviewers skim quickly, glance at the diff, and write "Looks good to me!" (LGTM).

⚠️ Bugs, architecture flaws, and security oversights slip straight through to production.

The Bite-Sized PR (< 250 Lines)

The Phenomenon: Reviewers read every line, test edge cases locally, and suggest meaningful architectural improvements.

✅ Reviewed within hours, merged quickly, and vastly reduces production regressions.

Conventional Comments: Healthy Team Vocabulary

Modern engineering teams use clear prefixes in code reviews to distinguish between non-negotiable fixes and optional thoughts:

Prefix Meaning Example
blocking: Must be fixed before approval. blocking: Missing auth check allows unauthenticated user deletes.
nit: Trivial cosmetic note (author can ignore). nit: Typo in log message: "retreive" -> "retrieve".
suggestion: Idea for cleaner code (author's choice). suggestion: We could use Array.find() here for readability.
question: Seeking understanding without blocking. question: What happens if the database returns an empty array?
