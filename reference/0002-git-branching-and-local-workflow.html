Git Branching & Local Workflow Reference

A visual cheat sheet for how developers work locally and coordinate changes via Git.

The 4 Zones of Git

Git separates code changes into four distinct state boundaries:

Zone What Lives Here Primary Command
1. Working Directory The live files an engineer sees and edits in VS Code or an IDE. File editing / saving
2. Staging Area (Index) The curated draft snapshot ready to be saved into history. git add <file>
3. Local Repository Committed history stored securely on the engineer's machine. git commit -m "msg"
4. Remote Repository The central team source of truth on GitHub or GitLab. git push / git pull

Branching Models Compared

Trunk-Based Development (Modern Standard)

Philosophy: Everyone branches directly from main, writes small incremental changes, and merges back within 1–2 days.

  • Zero merge hell: conflicts are tiny and resolved immediately.
  • Enables true Continuous Integration and high deployment frequency.
  • Requires feature flags to hide work-in-progress features in production.

GitFlow (Legacy / Release-Gated)

Philosophy: Long-lived parallel branches (develop, feature/*, release/*, hotfix/*) merged on calendar schedules.

  • Branches stay detached for weeks or months.
  • Severe "merge conflict debt" when long-running branches rejoin.
  • Favored by traditional teams with rigid manual release windows.

Common Terms Engineers Use in Standup

Phrase Plain-English Meaning
"Rebasing" Replaying your local branch on top of the latest team commits so your history is clean and linear.
"Merge Conflict" When two developers modified the exact same line of code and Git requires a human to decide which version survives.
"Dirty Tree" The local working directory has uncommitted edits that haven't been saved to Git yet.
"Headless State" Git is pointing directly to an older historical commit rather than a live branch.
