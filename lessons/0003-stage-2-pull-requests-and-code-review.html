Stage 2: Pull Requests & Peer Code Review

How engineering teams maintain quality, prevent bugs, and share knowledge before code merges.

What is a Pull Request (PR), Really?

Once an engineer finishes working on their local branch (Stage 1), they don't immediately push it into production. Instead, they open a Pull Request (PR) (called a Merge Request in GitLab).

A PR is not just a button—it is a structured conversation and inspection chamber. It asks the team: "Here is what I built, here is why I built it, and here is every line of code modified. Will you review and approve merging this into our main codebase?"

The Mental Model: Think of a PR as a legal contract amendment. The author highlights the proposed changes, reviewers inspect for loopholes or unintended side effects, and automated checks verify that basic regulations are satisfied before signing.

What Do Reviewers Actually Look For?

Effective teams separate code review into two distinct layers:

1. What Machines Check (Automated Linters & Bots)

Humans should never spend time debating formatting, missing semicolons, or sorting imports. Automated bots (Stage 3 CI) enforce stylistic and syntax rules before a human reviewer even opens the PR.

2. What Humans Check (Architecture & Logic)

Human reviewers focus strictly on high-leverage questions:

  • Architecture & Design: Does this solution fit our system patterns, or does it introduce unneeded complexity?
  • Edge Cases: What happens if the network drops, the user submits empty input, or the database is slow?
  • Security: Does this expose private user data or introduce SQL injection vulnerabilities?
  • Knowledge Sharing: Does another engineer on the team understand how this code works so we don't have a single point of failure?

The Secret Bottleneck: PR Turnaround Time

In many engineering organizations, developers write code in 4 hours—and then wait 4 days for a teammate to review and approve the PR.

When PRs sit idle, three damaging things happen:

  1. Context Switching: The author moves on to something else, forgetting details. When comments finally arrive, they must mentally reload the old task.
  2. Merge Conflicts: While the PR sits open, teammates merge other code into main, causing the unmerged branch to rot.
  3. Stagnant Lead Time: Team velocity is measured by when value reaches production, not when code is typed. Idle PRs destroy velocity.

💬 The Leadership Question

In your next engineering sync, ask:

"What is our median PR turnaround time from author submission to first review? Do our engineers feel blocked waiting on reviews, and how can we support faster turnaround?"

Elite teams target a PR review turnaround under 4 business hours. If your team averages 48+ hours, reducing PR size is usually the fastest fix.

📖 Primary Source Recommendation
